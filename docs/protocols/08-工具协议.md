## 1. 设计原则

| 原则 | 含义 |
|---|---|
| **受限** | 工具只能执行**已定义的业务能力**，不接受任意查询 |
| **参数化** | 所有 SQL 参数化；表名、列名、枚举值全部**白名单** |
| **只读** | 分析类工具一律用只读账号 `dsa_ro`（会话级强制只读） |
| **引用传递** | 大结果**不放进返回体**，写文件后返回**引用 + 摘要** |
| **错误可分辨** | 五类错误必须可区分，不得混为"失败" |
| **可追溯** | 调用保留 `tool_invocations` 中的参数、结果和哈希；实际SQL及绑定参数另入 `query_executions`，纯资源读取不虚构SQL |

## 2. 统一返回结构

```python
@dataclass(frozen=True, slots=True)
class ToolResult:
    ok: bool
    tool: str
    data: dict | None = None          # 内联数据，行数上限 MAX_INLINE_ROWS = 200
    refs: list[str] = ...             # 大结果的文件引用（相对 artifacts/ 的路径）
    summary: str = ""                 # 一句话摘要，供 LLM 阅读
    error: ToolError | None = None    # ok=False 时非空
    duration_ms: int = 0
    run_id: str | None = None
```

**关键约束**：

- `data` 中**任何列表的行数不得超过 `MAX_INLINE_ROWS`（200）**。
  超出时必须写文件并把路径放进 `refs`。
- `ToolResult` 必须可 JSON 序列化（提供 `to_dict()`）。
- `summary` 是**给人/LLM 读的**，不含大块数据；数值仍来自 `data`。

> 为什么限制内联行数：大结果进入 LLM 上下文会**同时**造成成本、延迟与精度问题。
> 让模型看到"有 42,613 行，前 10 行长这样，完整结果在 <路径>"，比塞进 42,613 行更有用。

## 3. 错误码

**五类必须可区分**——把它们混成一个"调用失败"，下游就无法决定该重试、该澄清还是该放弃。

| 错误码 | 类别 | 含义 | 典型触发 | HTTP |
|---|---|---|---|---|
| `E_TOOL_001` | 参数错误 | 参数类型/范围/枚举不合法 | `limit_n=-1`、`policy_kind` 不在白名单 | **400** |
| `E_PLAN_001` | 业务条件不足 | 参数合法，但业务口径不完整 | 未指定实验/窗口/触达比例；缺预期分配比例导致 SRM 无法检查 | **422** |
| `E_CAP_001` | 能力范围 | 该数据适配**不支持**此分析 | 请求日期窗口、请求净收益 | **422** |
| `E_DB_001` | 数据库异常 | 连接失败、权限不足、SQL 报错 | 数据库停机 | **503** |
| `E_DB_003` | 超时 | 超过 `statement_timeout` | 复杂查询超 10 秒 | **504** |
| `E_TOOL_999` | 未知（兜底） | 未归类的异常 | 程序 bug | **500** |

> **本表全部取自 docs/05-报告结构与异常分类.md（原工程文档引用，未纳入此快照） 的异常码注册表，不另立体系。**
> 其中 `E_TOOL_999` 是为工具层补录的兜底码（已同步登记到 docs/05 的 I 类）。
> 早期草稿曾用过 `E_TOOL_002` 表示"业务条件不足"——那是**重复造码**，
> docs/05 中已有 `E_PLAN_001` 承担该语义，已更正。

### 3.1 参数错误 vs 能力范围（**重要区分**）

| 情况 | 错误码 | 理由 |
|---|---|---|
| `experiment_key="不存在的实验"` | `E_CAP_001` | 参数格式合法，是**系统没有这个实验** |
| `limit_n=-1` | `E_TOOL_001` | 参数本身不合法 |
| `metric="conversion_rate"` 但数据集不支持该指标 | `E_CAP_001` | 是能力问题 |
| `metric=123`（类型错） | `E_TOOL_001` | 是参数问题 |

**判据**：**"写错了"是参数错误；"系统没有/不支持"是能力范围。**

这个区分直接影响用户体验：前者该让用户改输入，后者该告诉用户"这个功能本版本不做"。

## 4. 工具清单

| 工具 | 作用 | 主要参数 | 引用 | 输出 |
|---|---|---|---|---|
| `get_experiment_config` | 读实验配置 | `experiment_key` | — | 组别、窗口、预期比例来源及登记比较；不据登记字段冒称事前预注册 |
| `get_metric_definition` | 读指标定义 | `metric_id` | — | 分子、分母、单位、约束（读取包resources，仓库metrics副本须一致） |
| `query_arm_aggregates` | 分组聚合 | `experiment_key` | — | 各组 n / 购买率 / 访问率 / 人均消费 |
| `run_quality_checks` | 数据质量与识别条件检查 | `experiment_key`, `dataset_version` | — | 每项检查的 code/severity/passed/detail |
| `analyze_experiment_effect` | 效果推断 | 必需 `experiment_key`, `comparison_key`；可选 `metrics`, `n_boot`, `bootstrap_seed` | 按返回规则 | 结构化效果、区间、检验、单位、角色及阻断判定 |
| `get_model_registry` | 读模型登记 | `dataset_version?` | — | 模型元信息（特征列、参数、划分、代码版本） |
| `get_policy_evaluations` | 读策略评估 | `model_key` | — | 各策略各比例的增量估计与区间 |
| `get_customer_scores` | 取客户名单 | 必需 `model_key`；可选 `policy_kind`, `limit_n` | 超过内联上限时写引用 | 排序名单、摘要及产物引用 |
| `get_scoring_population` | 评分人群规模 | `model_key` | — | 可评分人数与分数口径，作为按比例名单的分母 |
| `describe_capability` | 数据适配能力 | `dataset_key` | — | 支持/不支持的分析类型 |

### 4.1 约束（每个工具都必须遵守）

1. **先校验参数，不合法直接返回 `E_TOOL_001`，不碰数据库。**
2. **分析类查询一律走只读引擎。**
3. 连接超时默认5秒；交互语句超时默认15秒，显式批处理档默认900秒。三者由config.py及环境变量配置，语句超时映射为 `E_DB_003`；连接超时不是查询运行上限。
4. 涉及"指标分母"的工具，其 SQL **不得**出现按干预后字段筛选的写法。

## 5. 结果引用结构

```python
refs: ["customer_scores/tlearner_lr_v1_uplift_top5000.csv"]
```

- 路径相对于已配置的 `ARTIFACTS_DIR`（默认项目artifacts/），便于迁移与审计。
- 解析后的绝对路径必须仍在产物目录内，越界拒绝。
- 引用与 `run_id` 关联，可通过 `analysis_runs.result_refs` 找回。

## 6. 运行记录

| 表 | 记录什么 | 关键字段 |
|---|---|---|
| `analysis_runs` | 一次业务运行 | `run_id`、可空`parent_run_id`、`status`、`stats_config`、`code_version`、`report_ref`、`result_refs` |
| `query_executions` | 实际SQL执行 | `run_id`、`seq`、`tool_name`、`sql_text`、`params`、`row_count`、`duration_ms`、`status`、`error_code` |

### 6.1 状态取值

`pending` → `running` → `succeeded` / `blocked` / `failed`

- `blocked`：质量/条件阻断，不输出因果结论；保留已读结构化证据不等于完成分析。
- `failed`：工具故障或能力限制等映射状态，须结合Agent终态说明。
- 等待用户保持pending；合法澄清/限制是否符合任务契约由评测判定，不以数据库status单独判成功。

### 6.2 重复执行检查

- `create_run` 支持调用方提供 `run_id`；同 `run_id` 重复创建**不新增行**。
- `record_query` 依赖 `UNIQUE(run_id, seq)`；重复调用 `DO UPDATE` 而非插入新行。
- 实际执行记录保留seq、参数、结果及run_id；效果重算使用真实子run_id保存新的SQL和差异，不能伪装覆盖父运行。

> 这条不是形式要求：LangGraph 的中断恢复**可能重新执行节点中的前置代码**
> （见《开发Agent的Skill与MCP配置建议.md》§2.3 的提醒）。
> 没有幂等保证，恢复一次就多一份重复产物。

## 7. 日志与敏感信息

**绝不写入日志**：数据库密码、API key、完整连接串。

- `dsa.config.Settings.describe()` 已实现脱敏（只输出主机/端口/库名/用户名，不输出密码）。
- 异常信息在返回前必须经过脱敏；有测试覆盖"构造含密码的异常，断言响应体与日志不含密码"。
- 请求日志字段：`run_id`、`tool`、`duration_ms`、`status`、`error_code`——**不含参数值中的敏感项**。

## 8. 服务接口

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/health` | 健康检查；DB 不可用时 `db_ok=false` 但**不返回 500** |
| GET | `/tools` | 列出可用工具及其 input schema |
| POST | `/tools/{tool_name}` | 调用工具 |
| GET | `/runs` | 运行记录列表（分页） |
| GET | `/runs/{run_id}` | 运行详情（含 query_executions） |
| GET | `/capability/{dataset_key}` | 数据适配能力说明 |
| GET | `/metrics/{metric_id}` | 指标定义 |

**统一错误响应体**：

```json
{"ok": false, "error": {"code": "E_CAP_001", "message": "...", "detail": "..."}}
```

## 9. 不需要 LLM 即可验证

阶段六验收条件要求「**使用固定调用脚本或接口检查工具链，无需 LLM 介入**」。

因此工具层必须能被一个纯 Python 脚本直接调用并断言结果——工具的输入输出
**不依赖任何 LLM 组件**。这既保证可测试性，也保证 LLM 只是**调用方**而非**依赖项**。
